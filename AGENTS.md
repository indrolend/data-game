# Agent contract — Digital Breakdown Godot migration

Goal: use Godot for rendering, input, scene organization, and presentation while cherry-picking the original C++ game as the behavioral source. Keep the original `Game` simulation authoritative wherever it already works. Port only missing or engine-specific pieces; document intentional omissions and later improvements instead of inventing replacement mechanics.

## Visual acceptance

- Follow `VISUAL_ACCEPTANCE.md`. Track behavior proof, presentation-contract proof, and visual acceptance independently in `evidence/visual-acceptance/ledger.json`.
- Headless tests, snapshot parity, source-byte equality, and a successfully saved PNG do not establish visual acceptance.
- Do not call visual work fixed, restored, final, verified, or parity-complete unless `tests/check_visual_acceptance.ps1` accepts a ledger case whose visual status is `accepted`.
- A Godot framebuffer driven by native state is still Godot evidence. New evidence names must identify the framebuffer renderer and must not use `native-*`, `final`, `ok`, `verified`, or `readable` as quality labels.
- Review the whole frame and record obvious defects before reporting the intended local change. An unresolved P0/P1 visual defect requires visual status `rejected` even if behavior and adapter contracts pass.
- Historical evidence directories are retained unchanged and their names confer no acceptance status.

## Architecture

- `godot/scenes/main.tscn` is the normal launch path and runs `main.gd` over the original C++ `Game` via `ParentGameNode`/`ParentBridge`. The original simulation remains the sole gameplay authority on this path; bridge ticks advance exactly `1.0f / 60.0f`.
- `godot/scenes/playable_runtime.tscn` and `playable_runtime.gd` are an isolated exploratory Godot-owned encounter, not the default game or a parity implementation. Keep its test separate; do not merge its mechanics into the parent-driven runtime unless each behavior is reconciled against the original C++ contract.
- `godot/scripts/player_controller.gd` owns Godot player movement, camera mode, hit points, attack-window timing, and player response to enemy damage. `godot/scripts/enemy_controller.gd` owns this encounter's approach, windup, strike, recovery, stagger, and defeat. `Area3D` overlap geometry determines valid melee/contact hits. These mechanics must not also be advanced by the original C++ simulation in this playable scene.
- `godot/scripts/phone_avatar.gd` is render-only. Its screen/body do not control movement or combat.
- `godot/scenes/parent_reference.tscn` is a retained alias for the parent-driven migration presentation. `parent/game/` is the unmodified archive-derived reference; do not edit it unless a concrete parent build/runtime blocker has first been reproduced and documented.
- `godot/scripts/main.gd` with `ParentGameNode` is the default parent-driven path. Preserve read-only snapshots, native fixed ticks, deterministic tests, and evidence; do not silently replace or weaken them.
- `godot/scripts/room_presentation_adapter.gd`, `godot/scripts/human_model_adapter.gd`, `godot/scripts/native_particle_presentation_adapter.gd`, and native presentation snapshots adapt the default parent-driven path. The human adapter uses original native-skinned model vertices, native `humanShellTriangleMissingTowardCrit`/armor values for render-only shell cracks, native `humanDamageSurfaceColor`/hit amount for render-only wound tint, and native tether anchor/destination/width for the vacuum beam. Particle instances copy `GameState::particles` and `particleMaterialColor` values; their camera-relative size cap is presentation-only, while native simulation/lifetime/velocity remain authoritative. Phone screen emission and its local light copy `PhoneDisplayLightingState` color/intensity/radius/offset/pulse; a small Godot-only pulse-to-energy curve is a rendering adaptation, and the light is parented to the render-only phone. Combat status and target attack-phase HUD cues read native snapshots only. These adapters own no combat/ingestion rules or collision. The room adapter renders native structures, lawn records, exact generated `FieldGrassTexture` and `CitySurfaceTexture` pixels, the checked-in 512x512 runtime `photo-stone` and `photo-metal` RGB maps, and 160 seeded low-detail `room_environment::grassBlade` records as render-only geometry, plus faceted rocks from `faceted_rock::makeVisualMesh`, HouseGeometry parts, two-part MarkerPillarGeometry, and RuinGeometry blocks/scars using source renderer color mappings. Field blade tips update from the original native `room_environment::grassTip` reaction contract using native player, shot, vacuum, and time state; placements remain cached by room key. Coastal's render-only subdivided water mesh uses native `CoastalWater` bounds/time/player state and the original analytical surface-height/wake formulas; `CoastalWaterSimulation` is not run by the gameplay loop and must not be promoted into a second simulation. Native material specular/shininess maps to Godot PBR response. Stone/metal maps are applied with Godot triplanar projection at native texture world scale; engine projection and Coastal shader are presentation adaptations, not pixel-matched desktop claims. House/marker/ruin transforms and surfaces, grass placements/tips/texture samples, Coastal state, phone display light fields, and target damage presentation values are direct-parent parity-compared. Keep stable IDs/transforms, create no gameplay collision, and skip object families without an appropriate visual contract. Bark/sand/sterile-tile map hookups and high-detail grass selection remain unported. Do not substitute arbitrary textures. Do not wire a ticking native simulation behind Godot-owned gameplay.
- City composition adapts `city_street::plan` into stable road, sidewalk, curb, gutter, intersection, crosswalk, center-marking, skyline body/cap, street-lamp, and service-cluster records; emits desktop-native obstacle boxes as render-only building masses with source plaster colors; and adapts `CityFacadeGrammar` into stable authored `.dbmesh` module records. Skyline window placement, sparse occupancy, warmth, and unlit material derive from the same native `city_facade` functions and time input. The traced C++ tree defines lamp/service placement formulas and quality-scaled counts, but no corresponding desktop draw path was found; their BoxMeshes are new Godot presentation additions, not recovered visual parity. `CITYLAMP`/`CITYSERVICE` verify snapshot-to-Godot transforms/materials and direct-parent snapshot consistency only. The adapter also parses original DBM1 facade triangle/material batches into cached ArrayMeshes. Native obstacle boxes remain the only collision/support authority. Native/Godot current-source captures are under `evidence/native-source-materials/native-current/`; City capture history is preserved under `evidence/native-city-*/`. The inspected first-person side-angle capture shows a recognizable lamp pole/head, but the bulb/arm and service cluster remain visually modest; no claim of source-renderer similarity is made. Skyline decoration beyond its native boxes/windows, complete building facade fixtures, exact desktop material/shadow parity, and broader quality/state coverage remain incomplete.
- `godot/scripts/hud_presentation_adapter.gd` is the single native-state HUD renderer for the default scene. It maps a subset of `DesktopRenderer::drawHud()` and receives native HUD/target/camera/player/signal/time snapshots. It owns no gameplay timers. `godot/tests/hud_presentation.gd` checks the authoritative battery/soul values, native camera FOV projection, snapshot sync, and that diagnostic/static duplicate HUD elements are absent; it explicitly frees the scene and fails nonzero. This is partial visual work, not exact HUD/menu parity.
- `native/lighting_presentation_snapshot.hpp` resolves native `ProgressiveCandidate` atmosphere, celestial daylight/sun direction, `RoomLighting`, and `SceneLightingResponse` for open-sky Field/City/Coastal rooms. Godot's incremental 64px sky resource and render-only sky dome consume native sky colors, daylight, and sun direction. The dome adds low-cost procedural profiles (stretched Field cirrus, broken City cloud, broad Coastal forms) and a correctly apparent-sized, limb-darkened sun disk; these are presentation silhouettes, not a meteorological simulation. The render-only Moon uses NASA LRO WAC color and LOLA elevation maps on a sphere whose direction and approximate 29.53059-native-day phase, 5.2-degree tilt, and 173.31-native-day eclipse-season rhythm derive from native time/sun state. The Moon is a presentation approximation, not an ephemeris: the game has no latitude, longitude, or civil date. Godot owns no gameplay clock or mechanics. Sterile remains a sealed static-color environment. `godot/tests/lighting_presentation.gd`, `godot/tests/lunar_visual_capture.gd`, and the `LIGHTING` parent parity row cover native state and resource contracts; GPU captures are required for visual claims. Original desktop shadow maps/material pixels, real-date astronomy/eclipse predictions, named constellations, and weather/cloud simulation are not claimed.
- Multiplayer source contract: `Game.hpp`/`Game.cpp` contain four-player state, sequenced `PlayerCommand`, host-side remote simulation, guest-side local prediction/correction, shared enemy targeting, downed/revive logic, and native snapshot application. The current migration checkout has no transport/session implementation (`DesktopMultiplayer`, socket/ENet layer, or host/join service), and `PhoneMenuMultiplayerAvailable` is intentionally false. Any Godot network integration must send validated semantic input to the native authoritative host and present returned native state; do not run parallel Godot gameplay or rely on scene replication for simulation. Do not claim multiplayer is ported until two independent processes pass authoritative behavior and disconnect/rejoin tests.
- The default path also exposes the native room-recompile upgrade state through `upgrade_presentation_snapshot()`. `hud_presentation_adapter.gd` renders the six native Shot/Lunge/Attack run/permanent choices; arrow input matches the original three-column/two-row navigation and activation calls `Game::chooseTemporaryUpgrade` or `Game::purchasePermanentUpgrade`. The adapter owns no token, cap, cost, or progression rules. `godot/tests/upgrade_presentation.gd` verifies state, input navigation, permanent token spend, temporary run-level increment, and resume; direct-parent parity includes the same transitions. Do not bypass the native APIs or let Godot advance run scaling.
- `godot/tests/room_transition.gd` starts from the original rally fixture, supplies native movement through a cleared room's doorway, and asserts the real `Game::updateRoomTopology()` transition increments the room and opens the native upgrade pause; it then runs the default scene sync and checks the room adapter reports the transitioned native room and floor transform. `ROOMCROSS` in the direct-parent/Godot parity suite compares the resulting frame, room, player transform, upgrade/pause, battery, and souls. This is a deterministic presentation-sync contract, not graphical multi-room verification.
- `PhoneMenuModel.hpp` and `PhoneDisplayLayout.hpp` are reused as the native menu model/layout contract. `ParentBridge` exposes semantic menu move/adjust/confirm/back operations and a read-only layout snapshot; Godot renders those native rows and forwards commands. The adapter owns no selection, settings, or page state. Offline menu/settings navigation and pause resume are covered; key-rebind capture, app exit, online host/join, and exact desktop phone-display visuals remain unsupported. `godot/tests/phone_presentation.gd` tests native layout and settings transitions; `phone-menu-playtest` GPU evidence demonstrates the current readability limitation.
- `tests/parent_reference.cpp` runs `Game` directly, without Godot. Its fixed scenario is the independent reference for the retained `parent_reference.tscn` path and `godot/tests/parent_parity.gd`.
- `godot/tests/parent_smoke.gd` explicitly frees every test-created Godot object. Failures must exit nonzero.
- `godot/tests/phone_presentation.gd` checks the native snapshot drives phone dimensions, screen offset/status, third-person transform, and first-person view-model placement; it explicitly frees the test scene and fails nonzero.
- `godot/scripts/agent_playtest.gd` supports validated semantic phone-menu and room-upgrade commands and captures ordered, synchronized frames. Invalid commands and failed captures must remain nonzero; preserve each command file, stdout/stderr log, exit code, and captures together under `evidence/`.
- `godot/tests/room_presentation.gd` checks native structures, lawn records, FieldGrass and CityAsphalt texture bytes/material hookups, exact source stone/metal runtime RGB bytes and their cached material/world-scale hookups, 160 native grass blade placements and native reaction tips; it checks the Coastal analytical water contract, native state uniforms and render-only/no-collision adapter, Sterile native substrate/material response, faceted-rock ArrayMesh vertices/normals, HouseGeometry, MarkerPillarGeometry, RuinGeometry parts/material colors/scars, and absence of Godot collision using original-game CityCourtyard, CoastalShore, SterileChamber, and Field fixtures. It explicitly frees created objects and fails nonzero.
- `godot/tests/human_model_presentation.gd` checks the original native model loads, deforms under native animation/body state, becomes a Godot `ArrayMesh`, and introduces no Godot collision; its controlled native interaction checks deterministic armor-driven triangle cracks and damage tint, Flesh/DigitalBlood particles, Environment shell fragments and the particle MultiMesh, plus native tether alignment. `godot/tests/phone_presentation.gd` also checks native display-light color/intensity/range/position and its increase when the native phone enters pause/menu mode.
- `godot/tests/playable_encounter.gd` exercises only the exploratory `playable_runtime.tscn` movement, floor/wall collision, enemy approach, melee contact, stagger, defeat, and enemy contact damage. Keep failing checks nonzero; this does not establish parity with the default game.
- `tests/compare_parity.ps1` compares structured reference and Godot snapshots with a default tolerance of `1e-5`.
- `MIGRATION_MATRIX.md` is the subsystem inventory, ownership map, dependency order, and definition-of-done contract. Update it when a subsystem boundary or status materially changes.

## Verification

Run `.\tests\verify.ps1` from the repository root in PowerShell. Launch the playable game with `godot_console.exe --path godot`. Equivalent build and retained reference commands are:

```powershell
cmake -S . -B build-godot47 "-DGODOT_CPP_DIR=C:/Users/indro/Projects/godot-cpp" "-DGODOTCPP_DEFAULT_API_VERSION=4.7"
cmake --build build-godot47 --config Release --parallel
godot_console.exe --headless --path godot --script res://tests/parent_smoke.gd
godot_console.exe --headless --path godot --quit-after 2
godot_console.exe --headless --path godot --script res://tests/phone_presentation.gd
.\tests\compare_parity.ps1
```

Keep the `GODOTCPP_DEFAULT_API_VERSION=4.7` definition quoted in PowerShell. An unquoted form was observed to split `4.7` and incorrectly select `extension_api-4.json`.

Logs belong in `evidence/`. Do not report a pass unless the command returned exit code zero.

## Current scope and rules

- The default scene runs the original C++ simulation and is verified headlessly for deterministic repeatability, movement, sprint, jump, mouse-look semantics, camera toggle, vacuum, native melee/target snapshots, communication signals, native pause, phone/room/model contracts, target interaction, upgrade selection/purchase/resume, and direct-parent/Godot parity. Headless checks do not establish graphical parity.
- Live Godot captures under `evidence/ui-restoration/` now show the HUD-cleanup slice in third-person, first-person, and a controlled combat/vacuum lifecycle. The subset HUD is not a complete `drawHud()` port; screenshots do not establish original visual parity. The world remains sparse compared with the original renderer.
- The default fixture begins with zero stored souls. The `start_rally_fixture()` test hook delegates to the original `Game::debugStartRallyLab()` and seeds one soul; headless checks and parity cover soul consumption and delayed projectile creation. The `start_target_fixture()` hook delegates to the original room-inspector enemy setup; headless checks and parity cover 20 live targets and deterministic target-state snapshots over neutral ticks. Those fixture targets remain stationary in that scenario. A separate 1,050-tick controlled interaction sequence covers shell defeat, ingestion, capture, and one soul entering inventory; it does not establish every enemy, soul variant, upgrade, or room-progression outcome.
- Field presentation uses original generated 64x64 RGB grass pixels, source-generated low-detail placements, and native `grassTip` reaction outputs for player/shot/vacuum interaction. Direct-parent `GRASSTIPS` parity and the adapter tip contract are tested. `evidence/native-field-coastal-sterile-final/` contains inspected RTX 3060 Godot frames for the updated Field/Coastal/Sterile slice. Blade shape/material remain Godot adaptations; high-detail selection, original shadows, and pixel-matched desktop visuals are not established.
- Coastal presentation uses the native analytical `CoastalWater` height/wake formulas and native room/player state in a render-only Godot shader. The separate `CoastalWaterSimulation` is unused by the authoritative gameplay tick.
- Sterile presentation maps native chamber/corridor geometry, marker pillars, lighting, substrate colors, and source material specular/shininess to Godot PBR response.
