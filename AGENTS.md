# Agent contract — Digital Breakdown Godot migration

Goal: use Godot for rendering, input, scene organization, and presentation while cherry-picking the original C++ game as the behavioral source. Keep the original `Game` simulation authoritative wherever it already works. Port only missing or engine-specific pieces; document intentional omissions and later improvements instead of inventing replacement mechanics.

## Architecture

- `godot/scenes/main.tscn` is the normal launch path and runs `main.gd` over the original C++ `Game` via `ParentGameNode`/`ParentBridge`. The original simulation remains the sole gameplay authority on this path; bridge ticks advance exactly `1.0f / 60.0f`.
- `godot/scenes/playable_runtime.tscn` and `playable_runtime.gd` are an isolated exploratory Godot-owned encounter, not the default game or a parity implementation. Keep its test separate; do not merge its mechanics into the parent-driven runtime unless each behavior is reconciled against the original C++ contract.
- `godot/scripts/player_controller.gd` owns Godot player movement, camera mode, hit points, attack-window timing, and player response to enemy damage. `godot/scripts/enemy_controller.gd` owns this encounter's approach, windup, strike, recovery, stagger, and defeat. `Area3D` overlap geometry determines valid melee/contact hits. These mechanics must not also be advanced by the original C++ simulation in this playable scene.
- `godot/scripts/phone_avatar.gd` is render-only. Its screen/body do not control movement or combat.
- `godot/scenes/parent_reference.tscn` is a retained alias for the parent-driven migration presentation. `parent/game/` is the unmodified archive-derived reference; do not edit it unless a concrete parent build/runtime blocker has first been reproduced and documented.
- `godot/scripts/main.gd` with `ParentGameNode` is the default parent-driven path. Preserve read-only snapshots, native fixed ticks, deterministic tests, and evidence; do not silently replace or weaken them.
- `godot/scripts/room_presentation_adapter.gd`, `godot/scripts/human_model_adapter.gd`, and native presentation snapshots adapt the default parent-driven path. The human adapter uses original native-skinned model vertices, native hit amount for render-only damage tint, and native tether anchor/destination/width for the vacuum beam. Combat status and target attack-phase HUD cues read native snapshots only. These adapters own no combat/ingestion rules or collision. The room adapter renders native structures, lawn records, faceted rocks from `faceted_rock::makeVisualMesh`, HouseGeometry parts, two-part MarkerPillarGeometry, and RuinGeometry blocks/scars using source renderer color mappings. House/marker/ruin transforms and surfaces are direct-parent parity-compared. Keep stable IDs/transforms, create no gameplay collision, and skip object families without an appropriate visual contract. Rock/house/marker/ruin texture pixels remain unported; do not substitute arbitrary textures. Do not wire a ticking native simulation behind Godot-owned gameplay.
- `godot/scripts/hud_presentation_adapter.gd` is the single native-state HUD renderer for the default scene. It maps a subset of `DesktopRenderer::drawHud()` and receives native HUD/target/camera/player/signal/time snapshots. It owns no gameplay timers. `godot/tests/hud_presentation.gd` checks the authoritative battery/soul values, native camera FOV projection, snapshot sync, and that diagnostic/static duplicate HUD elements are absent; it explicitly frees the scene and fails nonzero. This is partial visual work, not exact HUD/menu parity.
- `native/lighting_presentation_snapshot.hpp` resolves the existing static desktop atmosphere, `RoomLighting` rig, and `SceneLightingResponse` from native room/player/action state. The default scene maps those values to Godot environment, directional lights, and render-only point lights. It does not own a day cycle or gameplay state; Godot's point-light attenuation is an engine adaptation. `godot/tests/lighting_presentation.gd`, the `LIGHTING` parent parity row, and GPU evidence cover the contract. Original desktop shadow maps/material pixels are not claimed.
- The default path also exposes the native room-recompile upgrade state through `upgrade_presentation_snapshot()`. `hud_presentation_adapter.gd` renders the six native Shot/Lunge/Attack run/permanent choices; arrow input matches the original three-column/two-row navigation and activation calls `Game::chooseTemporaryUpgrade` or `Game::purchasePermanentUpgrade`. The adapter owns no token, cap, cost, or progression rules. `godot/tests/upgrade_presentation.gd` verifies state, input navigation, permanent token spend, temporary run-level increment, and resume; direct-parent parity includes the same transitions. Do not bypass the native APIs or let Godot advance run scaling.
- `godot/tests/room_transition.gd` starts from the original rally fixture, supplies native movement through a cleared room's doorway, and asserts the real `Game::updateRoomTopology()` transition increments the room and opens the native upgrade pause. `ROOMCROSS` in the direct-parent/Godot parity suite compares the resulting frame, room, player transform, upgrade/pause, battery, and souls. This is a deterministic transition contract, not graphical multi-room verification.
- `PhoneMenuModel.hpp` and `PhoneDisplayLayout.hpp` are reused as the native menu model/layout contract. `ParentBridge` exposes semantic menu move/adjust/confirm/back operations and a read-only layout snapshot; Godot renders those native rows and forwards commands. The adapter owns no selection, settings, or page state. Offline menu/settings navigation and pause resume are covered; key-rebind capture, app exit, online host/join, and exact desktop phone-display visuals remain unsupported. `godot/tests/phone_presentation.gd` tests native layout and settings transitions; `phone-menu-playtest` GPU evidence demonstrates the current readability limitation.
- `tests/parent_reference.cpp` runs `Game` directly, without Godot. Its fixed scenario is the independent reference for the retained `parent_reference.tscn` path and `godot/tests/parent_parity.gd`.
- `godot/tests/parent_smoke.gd` explicitly frees every test-created Godot object. Failures must exit nonzero.
- `godot/tests/phone_presentation.gd` checks the native snapshot drives phone dimensions, screen offset/status, third-person transform, and first-person view-model placement; it explicitly frees the test scene and fails nonzero.
- `godot/scripts/agent_playtest.gd` supports validated semantic phone-menu and room-upgrade commands and captures ordered, synchronized frames. Invalid commands and failed captures must remain nonzero; preserve each command file, stdout/stderr log, exit code, and captures together under `evidence/`.
- `godot/tests/room_presentation.gd` checks native structures, lawn records, faceted-rock ArrayMesh vertices/normals, HouseGeometry, MarkerPillarGeometry, and RuinGeometry parts/material colors/scars using original-game CityCourtyard, SterileChamber, and Field fixtures; it checks stable IDs/transforms, retained texture identity, and absence of Godot collision, explicitly frees created objects, and fails nonzero.
- `godot/tests/human_model_presentation.gd` checks the original native model loads, remains a triangle list, deforms under native animation/body state, becomes a Godot `ArrayMesh`, and introduces no Godot collision object; its controlled 1,050-tick parent interaction also checks that native tether state becomes a correctly aligned render-only Godot tether.
- `godot/tests/playable_encounter.gd` exercises only the exploratory `playable_runtime.tscn` movement, floor/wall collision, enemy approach, melee contact, stagger, defeat, and enemy contact damage. Keep failing checks nonzero; this does not establish parity with the default game.
- `tests/compare_parity.ps1` compares structured reference and Godot snapshots with a default tolerance of `1e-5`.
- `MIGRATION_MATRIX.md` is the subsystem inventory, ownership map, dependency order, and definition-of-done contract. Update it when a subsystem boundary or status materially changes.

## Verification

Run `.\tests\verify.ps1` from the repository root in PowerShell. Launch the playable game with `godot_console.exe --path godot`. Equivalent build and retained reference commands are:

```powershell
cmake -S . -B build-godot47 "-DGODOT_CPP_DIR=C:/Users/indro/Projects/godot-cpp" "-DGODOTCPP_DEFAULT_API_VERSION=4.7"
cmake --build build-godot47 --config Release --parallel
godot_console.exe --headless --path godot --script res://tests/parent_smoke.gd
godot_console.exe --headless --path godot --quit-after 2
godot_console.exe --headless --path godot --script res://tests/phone_presentation.gd
.\tests\compare_parity.ps1
```

Keep the `GODOTCPP_DEFAULT_API_VERSION=4.7` definition quoted in PowerShell. An unquoted form was observed to split `4.7` and incorrectly select `extension_api-4.json`.

Logs belong in `evidence/`. Do not report a pass unless the command returned exit code zero.

## Current scope and rules

- The default scene runs the original C++ simulation and is verified headlessly for deterministic repeatability, movement, sprint, jump, mouse-look semantics, camera toggle, vacuum, native melee/target snapshots, communication signals, native pause, phone/room/model contracts, target interaction, upgrade selection/purchase/resume, and direct-parent/Godot parity. Headless checks do not establish graphical parity.
- Live Godot captures under `evidence/ui-restoration/` now show the HUD-cleanup slice in third-person, first-person, and a controlled combat/vacuum lifecycle. The subset HUD is not a complete `drawHud()` port; screenshots do not establish original visual parity. The world remains sparse compared with the original renderer.
- The default fixture begins with zero stored souls. The `start_rally_fixture()` test hook delegates to the original `Game::debugStartRallyLab()` and seeds one soul; headless checks and parity cover soul consumption and delayed projectile creation. The `start_target_fixture()` hook delegates to the original room-inspector enemy setup; headless checks and parity cover 20 live targets and deterministic target-state snapshots over neutral ticks. Those fixture targets remain stationary in that scenario. A separate 1,050-tick controlled interaction sequence covers shell defeat, ingestion, capture, and one soul entering inventory; it does not establish every enemy, soul variant, upgrade, or room-progression outcome.
- The exploratory Godot encounter uses simple authored collision geometry and a stylized humanoid. It is not the default launch scene, a port of native enemy behavior, or evidence of gameplay parity. Keep its existing captures labeled as prototype evidence.
- Preserve existing evidence and dirty files. Do not weaken assertions, invent success, or hardcode expectations derived only from the Godot-facing runtime.
- Do not claim original renderer/assets, audio, complete controls, or full gameplay parity. Headless startup is not visual verification; graphical claims require inspecting captures of the exact scene and encounter state.
